# GPU 이니시에이터 설계

`notes/initiator-flow.md`의 단계를 CPU 대신 GPU가 할 때 무엇이 바뀌는지 정리한다.

## 원칙

읽을 때마다 하는 일은 GPU가 하고, 그때 GPU가 다루는 큐와 버퍼는 GPU 메모리에 둔다. 큐를 만드는 것처럼 한 번만 하는 일은 CPU가 해도 된다.

## I/O 큐 하나 연결

1. **큐 구조체 만들기**: 그대로.
2. **네트워크 카드 찾기**: 그대로.
3. **QP·CQ 만들기**: 바뀐다. GPU 메모리에 직접 만든다.
4. **연결 요청**: 그대로. SPDK가 QP를 직접 만드는 경우의 방식을 쓴다.
5. **연결 마무리**: 그대로. SPDK가 직접 만든 QP를 처리하는 방식을 쓴다.
6. **메모리 등록·버퍼 준비**: 바뀐다. 버퍼를 GPU 메모리에 두고 등록한다. 완료 버퍼를 수신 큐에 처음 올리는 일은 GPU가 한다.
7. **컨트롤러에 등록**: 바뀐다. Connect 명령을 GPU가 보내고 응답을 확인한다.

## 읽기 한 번

보내는 쪽:

1. **읽기 요청**: 바뀐다. GPU가 한다.
2. **연결 방식별로 넘김**: 없어진다. RDMA만 다룬다.
3. **명령 만들기**: 바뀐다. 기존에는 읽을 때마다 등록표에서 데이터 버퍼의 키를 찾아 명령에 적는다. 등록표는 CPU 메모리에 있어서, GPU가 쓰려면 GPU로 복사해 계속 맞춰 줘야 하고 읽을 때마다 표를 뒤져야 한다. 그래서 **명령 버퍼마다 데이터 버퍼를 하나씩 정해 두고, 큐를 만들 때 CPU가 주소·키·명령 번호를 미리 적어 둔다.** 읽을 때 GPU는 빈 명령 버퍼를 골라 블록 번호만 적는다.
4. **보내기**: 바뀐다. GPU가 송신 큐에 넣고 카드에 알린다.

타겟이 데이터를 써 넣고 완료를 보내는 부분은 그대로다.

받는 쪽:

5. **완료 확인 부르기**: 바뀐다. GPU가 한다.
6. **CQ에서 완료 꺼내기**: 바뀐다. GPU가 한다.
7. **어느 요청이 끝났는지 찾기**: 바뀐다. 완료 버퍼를 수신 큐에 다시 올리는 일과 송신 완료 확인을 GPU가 한다.
8. **콜백**: 없어진다. 끝난 명령 버퍼 번호를 돌려주면, 부른 GPU 코드가 정해진 데이터 버퍼를 처리한다.

## 환경별 처리

Hopper 이전 GPU에서는 네트워크 카드가 데이터를 먼저 쓰고 완료를 나중에 써도, GPU에서는 완료가 먼저 보일 수 있다. 그래서 이 환경에서는 완료를 확인한 뒤 데이터를 읽기 전에 순서를 맞추는 처리를 넣는다. GPU 코드는 아키텍처별로 컴파일되므로 `#if __CUDA_ARCH__ < 900`으로 이 환경에서만 넣는다. 네트워크 카드 종류에도 달려 있는지는 구현할 때 확인한다.
