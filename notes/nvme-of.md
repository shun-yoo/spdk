# NVMe-oF (네트워크 부분)

## 타겟과 이니시에이터

- **타겟**: SSD가 꽂힌 서버. 네트워크로 받은 요청을 자기 SSD에서 처리하고 결과를 돌려준다. SPDK에서는 `nvmf_tgt` 프로그램이 이 일을 한다(`app/nvmf_tgt/`, 코드는 `lib/nvmf/`).
- **이니시에이터**: 요청을 보내는 쪽.

NVMe-oF는 **둘 사이의 대화 규칙**이다. 명령을 네트워크 메시지에 담는 법, 데이터를 넘기는 법, 완료를 돌려주는 법을 정한다. 받은 요청을 실제로 처리하는 것은 타겟 안쪽(bdev 이하)의 일이다([spdk-overview.md](spdk-overview.md) 참고).

## 컨트롤러와 네임스페이스

- **컨트롤러**: NVMe SSD에서 명령을 받아 처리하는 부분을 컨트롤러라고 한다. 타겟은 연결마다 가상의 컨트롤러를 하나 만들어 주고, 이니시에이터에게는 이것이 네트워크 너머의 SSD 한 개로 보인다.
- **네임스페이스**: 컨트롤러 뒤에 있는 실제 저장 공간. "네임스페이스 1번"처럼 번호로 부른다.

## 큐

**큐**는 원격 SSD에 명령을 보내는 통로다. 두 종류가 있다.

- **admin 큐** (큐 번호 0): 설정·조회용. SSD 켜기, 정보 묻기, keep-alive(연결이 살아 있다는 신호). 연결할 때와 끊을 때 주로 쓰고, 읽기 중에는 거의 쉰다.
- **I/O 큐** (1번부터): 읽기·쓰기용. 여러 개 만들 수 있고, 보통 스레드마다 하나씩 쓴다.

네트워크 너머에서는 큐 하나를 **RDMA 연결 하나**로 만든다. 이니시에이터와 타겟이 각자 아래 두 부품을 갖고 있고, 양쪽의 QP를 서로 이어 놓은 것이 RDMA 연결이다.

- **QP**: 송신 큐와 수신 큐 한 쌍
- **CQ**: 완료 큐. 송신·수신이 끝날 때마다 완료 항목이 쌓인다. 양쪽 CQ는 서로 연결되지 않고, 각자 자기 QP에서 일어난 일만 받는다. 메시지가 오면 받는 쪽 네트워크 카드가 받는 쪽 CQ에 적는다.

## rdma_cm

큐 하나마다 RDMA 연결을 하나씩 맺어야 하는데, 이 연결을 IP 주소로 맺게 해 주는 라이브러리가 rdma_cm이다. TCP의 `connect`/`accept`와 비슷한 역할이다. admin 큐를 연결할 때도, I/O 큐를 하나씩 연결할 때도 매번 쓴다.

- 이 IP까지 어느 네트워크 카드, 어느 길로 가야 하는지 찾아 준다.
- 양쪽이 연결 정보(QP 번호 등)를 주고받게 해 준다.

NVMe-oF는 연결을 요청할 때 큐 번호, 큐 크기, 컨트롤러 번호를 같이 실어 보낸다.

## 준비 과정

1. **admin 작업**: 원격 SSD를 쓸 수 있게 켜고 정보를 묻는다. 결과로 남는 것은 세 가지다.
   - 컨트롤러 번호(cntlid). I/O 큐를 붙일 때 쓴다.
   - 블록 크기
   - 쓸 수 있는 I/O 큐 개수
2. **I/O 큐 만들기**: 읽기 통로를 만든다. RDMA 연결을 맺고, 그 큐로 Fabrics Connect 명령을 보내 컨트롤러에 붙인다.
3. 그다음부터 읽기·쓰기를 한다.

코드 기준의 자세한 흐름은 initiator-flow.md에 정리한다.

## 읽기 한 번이 오가는 모양

1. 이니시에이터가 완료를 받을 **수신 버퍼를 미리 걸어 둔다**. 이게 없으면 타겟의 완료 메시지가 갈 곳이 없다.
2. 이니시에이터 → 타겟: **명령(64바이트)을 보낸다.** 명령에는 "몇 번 블록부터 몇 개 읽기", 데이터를 받을 내 메모리 주소와 그 메모리의 키, 명령 번호(cid)가 들어 있다.
3. 타겟: SSD에서 읽은 데이터를 **이니시에이터 메모리에 바로 써 넣는다**(RDMA write). 이니시에이터 CPU는 이 과정에 끼지 않는다.
4. 타겟 → 이니시에이터: **완료(16바이트)를 보낸다.** 완료에 들어 있는 명령 번호로 어느 요청이 끝났는지 안다.

RDMA write는 받는 쪽 CPU를 쓰지 않으려고 만든 방식이라, 받는 쪽 CQ에 완료 항목을 남기지 않는다. 그래서 4번 완료 메시지가 "데이터가 다 왔다"는 신호 역할도 한다. 같은 연결 안에서는 보낸 순서대로 도착하므로, 완료가 왔으면 데이터는 이미 와 있다.

## 타겟 안에서 요청이 지나가는 길

1. NVMe-oF 타겟이 네트워크로 명령을 받는다 (`lib/nvmf/`, RDMA는 `lib/nvmf/rdma.c`).
2. bdev로 넘긴다 (`lib/bdev/`). 여러 SSD를 묶었다면 RAID bdev(`module/bdev/raid/`)가 요청을 SSD별로 나눈다.
3. NVMe bdev(`module/bdev/nvme/`)가 직접 제어 코드(`lib/nvme/nvme_pcie.c`)로 SSD에 명령을 낸다.
4. 끝나면 거꾸로 올라가, 타겟이 데이터와 완료를 이니시에이터에게 보낸다.

## 이니시에이터 종류

| 이니시에이터 | 누가 요청을 보내나 | 코드 |
|---|---|---|
| 리눅스 커널 (`nvme connect`) | CPU, 커널을 거침. `/dev/nvmeXnY` 블록 장치로 보인다 | 리눅스 커널 `drivers/nvme/host/rdma.c` |
| SPDK | CPU, 커널을 거치지 않고 polling | `lib/nvme/nvme_rdma.c` |
| GPU가 직접 | GPU | 이 포크에서 만들 것 (design/ 참고) |
